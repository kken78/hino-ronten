# 論点ノート：自治体経営の基盤として（2026-10-25）

hino-ronten のこれまでの設計と作業を、自治体経営の基盤という見方で整理し直したもの。依頼者の指摘（2026-10-25）を受けて書いた。進め方の決定は DESIGN.md ADR-20 にある。

---

## 1. 3つの柱

論点ノートが支えようとしているものは、まとめると自治体経営の基盤である。次の3つの柱に分けて考える。

| 柱 | 中身 | 論点ノートの中で当たるもの |
| --- | --- | --- |
| A. ステークホルダーとの連携 | 議会・住民・関係者と、事業の目的・課題・経緯を共有し、議論すべきテーマを見つける | 論点編、議会でのやりとりの記録、住民向けの説明、懇話会などの過程の記録 |
| B. 庁内組織のマネジメント | 将来に向けての意思決定（計画・予算）と、執行管理（実施・決算・見直し）。議会での議論を節目として、事業を回す | プロジェクトマネジメント編（事業のロジックモデル、予算要求・決算説明の準備、議会の節目）、答弁作成、研修 |
| C. 業務効率化と相互運用性 | 資料を一度整えれば、議員・職員・住民・ほかのシステムが同じものを使える。そのためのデータモデル | 資料編の土台、キー・台帳・記録、入力の版の固定 |

3つの柱に共通する前提：

- 示す情報源は公開情報で、公開情報からどこまで役立つものを示せるかを確認する
- 評価や結論は書かない。議員を件数で並べない（画面と出力の決まり）
- 意思決定に至る過程（コンテキスト）を、資料と出典つきで残す

## 2. 参照する考え方

| 考え方 | 要点 | 論点ノートでの使い道 | 柱 |
| --- | --- | --- | --- |
| 公文書管理法 第4条・第34条 | 行政機関の職員は「経緯も含めた意思決定に至る過程並びに当該行政機関の事務及び事業の実績を合理的に跡付け、又は検証することができるよう」文書を作成する（第4条）。地方公共団体は、法の趣旨にのっとり文書の適正な管理に努める（第34条） | 過程の記録・事柄の記録・つながりの記録は、公開された資料の範囲で、意思決定の過程を跡付けるためのもの、と位置づけられる。コンテキストの残し方の説明の軸になる | A・B |
| 議会の政策サイクル（飯田市議会の例） | 住民との意見交換会 → 政策提言 → 議会による行政評価 → 決算審査 → 予算要望 → 予算審議、を回す。行政評価と決算審査を連動させる | 議会での議論を、事業の1年の節目（予算審議・決算審査）に置く考え方の根拠。プロジェクトマネジメント編の節目の並べ方 | A・B |
| EBPM とロジックモデル（内閣官房 行政改革推進本部事務局） | 各府省はロジックモデルを作成・活用した EBPM を実践し、行政事業レビューや予算要求の説明で一部の事業が使っている | プロジェクトマネジメント編で、担当者が事業のロジックモデルを組み立て、予算要求・決算説明に使う、という形の根拠 | B |
| 計画・予算・評価の連動 | 総合計画を軸に、予算と評価をつなげて回す自治体経営の考え方（多くの自治体の総合計画で使われている。拠りどころにする文献は、まだ確認していない） | 資料編（総合計画・実施計画・附表・決算をつなぐ）の目標の置き方 | B・C |
| 政府相互運用性フレームワーク（GIF、デジタル庁） | コア語彙・コアデータパーツ（日付・住所などの値の形式）・コアデータモデル（個人・法人・施設など）・実装データモデル、の層でデータを整える | キーと値の形式（日付の形、名前のそろえ方）を、層に分けて決める考え方 | C |
| Popolo・Open Civic Data | 議会・行政の透明性のためのデータで、人（Person）・組織（Organization）を共通の形にし、議案（Bill）・採決（Vote）・会議（Event）などを定める | 議員のキー、会議・議案のキーを、ほかの議会データとつなげられる形で持つ考え方 | C |

出典は末尾。

## 3. 現状を3つの柱に当てはめる

| 柱 | できているもの | 欠けているもの |
| --- | --- | --- |
| A | 会議録・議会だよりの取り込み（ほかのリポジトリ）、計画への言及の台帳、やりとりの記録・過程の記録の決まり（ADR-16・19）、懇話会と広報ひのの取り込み | 使う人に見える形（画面）、確定した記録 |
| B | 附表と実施計画の対応（令和8年度・181事業）、議会の議案と結果、ADR-18（節目の考え方） | 事業ごとの予算の年次の流れ（令和3〜7年度の附表は hino-town-docs にあるが、つないでいない）、実施計画の版（ADR-11。shiga-hino-plans への依頼がまだ）、決算・成果の資料（町のサイトに無い。判断事項10）、プロジェクトマネジメント編の形 |
| C | 4つの入力の版の固定、キー・台帳・記録の決まり、検査の道具（台帳） | 議員のキー、事柄と記載の表（名前の揺れを止める）、記録の検査の道具、ほかのデータとの対応（議会だよりと会議録の問いの対応など） |

見えてきたこと：

- C は先に進みすぎ、A と B の「使う人に見えるもの」が無い
- B のプロジェクトマネジメント編は、ADR-18 に書いただけで、形がまだ無い
- データモデルを、使う人の反応を見ないうちに何度も直している（2026-10-24 だけで ADR-15 → 16 → 19）。進め方は DESIGN.md ADR-20 で改めた

## 4. 作業を止める条件と見直す時点

### 4.1 いつも当てはめる条件（CLAUDE.md の「進め方」にも書く）

次のどれかに当たったら、作業を止め、この文書（3つの柱と趣旨）に沿って見直してから進める。

1. 同じ設計の点を、2回直すことになったとき
2. 前に決めた ADR と食い違う変更が要るとき
3. 人の判定にかかる手間が、その工程で見込んだ時間を超えそうなとき。手間は行の数だけでは決まらず、判定の中身による。超えそうなときは、判定の見せ方（同じ書き方の行をまとめて示す、など）か、記録の量や形を見直す。人が判定する工程では、判定を頼む前に、行の数・行の種類・見せ方・見込みの時間を依頼者に示す
4. 使う人に見える物に近づかない作業（文書・台帳・道具の直し）が、3回続いたとき
5. 3つの柱のどれにも当たらない作業が出てきたとき

### 4.2 工程ごとの見直す時点

工程の名前は DESIGN.md §5（2026-10-25）の S0〜S7 による。

| 時点 | 確認すること |
| --- | --- |
| S0 のあと | 直しが3枚に要る分だけか。ほかの直しを持ち込んでいないか |
| S3 のあと | 判定にかかった時間と、見込みとの差。超えたときは、判定の見せ方か、記録の量や形を見直す |
| S5 のあと（見せる前） | 3枚が、3つの柱のそれぞれに当たっているか。評価や結論を書いていないか |
| S7（見せたあと） | データモデル・進め方を、反応に合わせて直すか。2つめの事業・テーマに広げるか |
| 2つめのテーマの前 | 幼保の形（懇話会 → 提言 → 計画）に固定されていないか（判断事項18） |
| 基盤（Cloudflare・AWS）を作る前 | 試作の画面と生成AIの出力が、評価の基準（docs/eval-shisaku1.md）を満たしているか（ADR-13） |
