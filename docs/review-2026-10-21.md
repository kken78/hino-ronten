### 2.1 変えないところ

- 台帳の形を、照合方法によらず共通にしている：11列、(from, to, method) で1行、candidate・confirmed・rejected の3状態。附表のように性質の違う対応も、列を足さずに載った。program などの照合方法も同じ形で足せる

## 4. 初期の企画からの練り直し

### 4.1 初期の企画の構成

初期の企画（2026-10-09）は、機能を4つに分け、メニューで切り替える形だった。

| 機能 | 内容 | 利用者 |
| --- | --- | --- |
| 資料編 | 事業ごとに目的・予算・実績・成果指標を一覧にし、出典を示す | 職員・議員（最終的に一般公開） |
| 論点編 | 資料編の内容を比較し、論点を示す | 職員・議員（最終的に一般公開） |
| プロジェクトマネジメント編 | 担当事業のロジックモデル、予算要求・決算説明の文案 | 職員 |
| ロールプレイ研修 | 議会答弁・住民説明・予算査定の練習 | 職員 |

このほか、管理の画面としてプロンプト台帳があった。資料の種類と加工の段階（資料 → 論点）で画面を分けており、利用者が何のために来るかは、画面の分け方に入っていなかった。

### 4.2 練り直しの考え方

1. 入口を、機能からテーマに替える。利用者は「この件について」で来る。テーマは、総合計画の分野・基本施策、個別の計画、事業のどれでもよい。資料編と論点編は、テーマごとの1つの画面（テーマのノート）の中の1つの部分にまとめる
2. 共有の資料と、各自の作業を分ける。テーマのノートは誰が見ても同じ中立の資料で、評価や結論を書かない（EDITORIAL_POLICY）。質問の準備や答弁の準備は、その上で各自が行う作業で、立場がある。作業の中身は本人だけのものとし、職員と議員の間で見えないようにする。出典を必ず付けることは、どちらにも同じく求める
3. 時の流れを軸の1つにする。議論の根拠は「いつ、何が決まり、何が言われたか」であり、計画・予算・議会を1本の時系列に並べる。派生の場面（意思決定の検証、振り返り、研修）は、どれもこの時系列を使う
4. 立場ごとの作業は、同じ資料の上の使い方の違いとして作る。議員の「質問の準備」と職員の「答弁の準備」は同じ画面の型で、出力の形だけが違う
5. 派生の場面は、テーマのノートと時系列を使い回し、新しい資料を持たない（初期の企画の「PM編・ロールプレイは資料編を参照するだけで変更しない」を引き継ぐ）

| U2 | 答弁の準備 | 職員 | これまでの答弁（食い違いが無いか）、計画と予算の記載、想定される再質問。答弁の骨子（出典つき） | テーマのノート、準備の作業台 |

## 5. 試作で決めておく点と、要る対応

### 5.1 共有の資料と各自の作業の分け方（ADR-12 として提案）

- 共有の資料（テーマのノート・経緯）：中立。評価や結論を書かない。AI が文を作るときも、比べて分かる事実までとする。職員が確認してから見せる
- 各自の作業（準備の作業台・研修）：立場がある。作った骨子は本人の下書きで、本人のものとする。他の利用者には見えない。職員の作業を議員が、議員の作業を職員が見られないことを、仕組みとして保証する
- どちらも、出典の無い文は出さない。各自の作業で、利用者が自分で書いた文は出典を求めないが、AI が作る文には出典を付ける
- 議員と職員が同じ基盤を使うため、この分け方は信頼の前提になる。試作の説明でも最初に示す

### 5.2 データの区分と、試作の段階

- 準備の作業台に入るもの（通告前の質問案、答弁の案）は公開情報ではない。庁内区分と同じく国内の処理先でしか扱えない（ADR-9）。判断事項9（段階0の試作を職員・議員に使ってもらうか）は、これを踏まえて決める必要がある
- 段階を3つに分けることを提案する
  - 試作1：AI なし、公開情報だけ。テーマのノートと経緯の検証を、題材1つで作る。台帳と入力から機械的に作れる範囲
  - 試作2：AI あり、公開情報だけ、練習用。準備の作業台と研修を、架空の質問や過去の実際の質問を題材に使う。利用者の実際の下書きは入れない
  - 試作3：国内の処理先。実際の答弁・質問の準備に使う

### 5.3 データ構造の対応

| 記号 | 対応 | いまの状況 |
| --- | --- | --- |
| a | テーマの定義を置く参照表（例 `ref/themes.tsv`）。テーマごとに、含める計画・総合計画の分野と基本施策・事業のキーを、人が根拠つきで書く | 無い。題材1つ分から作る |
| b | 柱・分野の共通の軸 | sogo6.json の node（分野34・基本施策）を使う。実施計画の分野（分野①など、key が無い）と sogo6 の分野の対応は、番号と名前で表にする。実施計画には分野㉜ 公共施設が無いなど、そろわない箇所がある |

| d | その時点の資料（版） | 手直し1（実施計画の版）を広げた問題。youho のように一部改正のある計画もある。経緯の検証で「その時点で参照できた資料」を示すには、計画の版ごとの区別が要る。shiga-hino-plans と相談する |
| e | 質問と答弁の区別 | 会議録の発言に role（議員は「8番」などの議席、当局は「町長」「○○課長」など、議長は「議長」）がある。hino-council-search の画面も同じ規則で分けている。議会だよりの答弁は、多くが「答弁」とだけあり、答えた人は会議録で確認する |
| f | 議案と採決 | hino-council-search の `public/data/gian.json`（会議ごとの議案と結果）と `proceedings.json` の採決・討論の場面にある。いまの lock の files には入っていない。経緯の検証に使うなら lock に足す |
| g | 事業の単位の議会リンク | 無い（工程8の program 照合）。題材は計画の単位の言及で始められる |
| h | 画面が読むデータの形 | 無い。テーマごとに、確定していて照合が一致した行だけを、名前・日付・出典の URL・データの時点と組み合わせた JSON を作る。LINK_SCHEMA と同じく、先に文書で決める |

§1〜§6 は 2026-10-21 の検討の記録で、書き換えない。そのあと依頼者と決めたことを、この節に日付を付けて足す。§5.1 と §5.2 の案は、7.1・7.2 で改めた。

### 7.1 共有の資料と各自の作業（§5.1 を改める。2026-10-21）

依頼者の指示：

- ログイン機構は当面いらない。採らなかった案や却下したものも含めて、それぞれの立場（議員・職員）の見方が並んで見える画面にする
- 各人は業務で使える生成AIを持っている（職員は LoGoAIアシスタント。RAG に入れられるのは DOC・PDF ファイル）。この基盤でやりとりしたものを各自の生成AIに持ち込み、個別に検討を深める形でよい。職員なら、LoGoAIアシスタントの RAG に入れるデータソースや、汎用的・特徴的なケースに使えるプロンプトのひな形を作る基盤とする
- 作業を共有する範囲と、管理者が中身を見ない仕組みは、未定でよい。試作の段階では、サーバーに保存しない
- 深い検討は、この基盤の中の生成AIと各自の生成AIの併用とする。初期の段階から、低コストで基盤の中の生成AIの処理は残す（応答の速さと、出力の姿をつかむため）。それ以上の費用をかけるかは先の話
- 出力の水準を、生成AIのモデルやエフォートの違いで片付けないようにする（「深い検討をしたいなら自前の生成AIを使えばよい」で済ませない）

これにより、§5.1 の「各自の作業の中身は本人だけのものとし、職員と議員の間で見えないことを仕組みとして保証する」は採らない。DESIGN.md の ADR-12 に書いた。

### 7.2 試作の段階と題材（§5.2・§4.5 を改める。2026-10-21）

### 7.6 事業ごとの整理と、深い議論を促す論点（2026-10-24）

依頼者の提示：

- 一般質問でのやりとりを基にしたテーマのノートは、最初の工程としてよい
- 議員と役場の間で、総合計画や予算の事業ごとに、その目的・目標・問題・課題を分かりやすく構造化して、議論すべきテーマを共有したいという議論が進んでいる。それをまとめる作業が非常に煩雑で、効率化を図りたい。その過程で漏れてしまうかもしれない、深い議論を促す論点の提示を、この仕組みの中でアシストしたい
- 議員と役場の議論で使っている決まった様式は、いまは無い
- 最初の単位は、実施計画の事業とする

これを受けて、事業ごとの整理シートと論点の型を、試作1に組み込む（DESIGN.md ADR-15）。

### 7.7 議会での議論の読み方と、サービスの位置づけ（2026-10-24）

7.6 を受けて、論点の候補を言葉の一致で組み合わせる形（指標と事業を語でつなぐ案）を検討したが、依頼者の指摘で採らないことにした。計画・実施計画・予算は、それぞれが前提にしている事業のロジックモデル（課題→投入→活動→結果→成果→めざす姿）を持っているはずだが、分かりやすく書かれていない。そのため議論の元にできていない。語の一致で関連づけを探すと、抜けている箇所を語で埋めることになり、かえって分かりにくくなる。

依頼者の提示（議会での議論の読み方）：

- 一般質問の会議録と、それを要約した議会だよりは、良いお手本になる。議員（その背後には住民）が何を知りたいと思い、当局から何を引き出したか（引き出せなかったか）が記録されている。この見方は、ほかの論点の取り出しにも使える。議会での答弁が無いものでも、同じ枠組みで仮のやりとりを作れる。いつもと違うやりとりをしているときに、どこが違うのかを見分けることにも使える
- 議会の運び方：最初の問いには、町長（教育委員会の所管は教育長）が方針の方向を答える。細かい点は、再質問以降に課長・主監が答える。特別職が補うこともある
- 一問一答の形は、事実を確認するために使われる
- 議員の問いは再々質問までで、そのあとは要望になる。問いと答えがかみ合うこともあれば、かみ合わないこともある
- 議論が深まったものもあれば、確認にとどまるものもある。確認の議論にも意味がある
- 「こう議論すればよかった」は、記録からは組み立てられない。計画・予算・方針や、文章になっていない前提の論理、社会の背景から評価して補う必要があり、生成AIで補うことも考えられる
- 生成AIを使って作った情報は、公開している情報源に入れない。補うのは画面の上で行う
- もとの設計の意図：研修は、お手本を学び、身に付いた度合いを測り、次に回す形にしたい。答弁作成は、抜け漏れや矛盾をまとまった形で確認する手順にしたい
- 議会での議論は、事業の運営（プロジェクトマネジメント）の節目の一つである。最大の節目は予算審議である
- 公開情報から、議員と職員それぞれの準備（一般質問や答弁の準備）や、事業の運営に、どこまで役立つものを示せるかを確認する

幼保の一般質問10問の書き出し（下書き。リポジトリの外に置いた）で分かったこと：

- 最初の問いは、いくつかの点を一度に問い、町長が点ごとに答える。具体的な数字は、主に再質問への課長の答えに出てくる
- 議会だよりは、最初の問いと町長の答えを載せ、再質問以降は載せないことが多い。議会の運び方からみて、方針の方向を載せる編集である。言い回しの違いもある（「現時点では」が落ちる、「頃」が「まで」になる、など）
- 問いをロジックモデルの区分で分けると、活動73、手続き54、結果46、投入34、課題14、成果8、めざす姿5だった。成果（それで何が変わるか）を問うものが少ない
- 答え337のうち53が、時期や中身を後に回す答え（留保）だった。「考えていない」という答えは、留保とは別に分ける
- 同じ点が会議をまたいで問われる。新こども園の面積 2,800㎡ の根拠は、2024年12月から2025年3月までに少なくとも3回問われた。定員は、2024年12月に「基本構想策定の中で決めていきたい」と答え、2025年12月に「285」と答えた
- データの課題：会議録の審議の記録で、1つの発言が複数の問いにまたがるものが10問中5問にあった（hino-council-search）。議会だよりの問いの文に、切れて読めない箇所があった（council-dashboard）

会議録のデータから読める節目の時期：予算の委員長報告は3月の定例会議の最終日（2025年3月24日、2026年3月23日）、決算の委員長報告は12月の定例会議の初日（2024年12月2日、2025年12月1日）。

これを受けて、論点の示し方を ADR-16、生成AIの補足の扱いを ADR-17、サービスの位置づけを ADR-18 として DESIGN.md に書いた。ADR-15 の論点の型は ADR-16 で改めた。細部は試作1で直す。

### 7.8 政策の過程、事柄の時点、記載どうしのつながり（2026-10-24）

7.7 のあと、U3 の文書を作り直す中で、整理シートの記載をロジックモデルの区分のどれかに置く案を出したが、依頼者の指摘で改めた。

依頼者の提示：

- 再編整備計画に至るまでに、町民や関係者とのグループワークなどを行った懇話会での議論や報告書がある。そのことも議会の場で議論されており、そうしたことを踏まえて整備計画として結実している。基本方針の項目だけを取り上げるのでは足りない。資料の範囲と、スキーマの単純化の、どちらか（あるいはどちらも）による
- 行政の政策立案やその過程での議論、実施の段階での検証には、言葉にしにくい点、構造にしにくい点がある。コンテキストをどこに残すかという観点でも、この取り組みが、ほかの自治体にも示唆を与えるものになるとよい
- 懇話会であれば設置要綱がある、といった根拠など、周りの情報も大切である。そうした網羅のしかたをどう構造化するかは、あとで検討できるようにしておく。ほかのテーマでは、今回のこども園のような形以外の現れ方がありうる（町長選挙での公約なども）
- 公開されている情報は、すべて取り込むという考え方である。ただし広報ひのは、すべての記事を取り込む必要はなく、記事の構造を調べて、要る範囲でよい
- 広報ひのの記事には、発表されたあとに載るもの、発表と同時に載るもの、今後の予定として載るものがある。政策の中身の変わり目を確認するのに広報ひのは向いているが、だからこそ時点の取り方に注意が要る。途中で予定が変わることもある。新しいこども園は、直近の広報ひのと議会で、開園が1年延期になっており、理由も書かれている。そこが大事な事実で根拠になる

確認したこと：

- 会議録で、懇話会にふれた発言は、2021年12月から2025年6月までに約70件ある。2021年12月に子ども支援課長が懇話会の立ち上げを答え、2024年9月の議員の問いでは「令和４年７月から本年２月まで、全10回の懇話会、各層のワークショップ37回、先進地視察４か所、シンポジウムの開催など」とある。2024年12月と2025年3月に、町長が「再編整備計画（案）は…懇話会の提言を基に策定」と答えた
- 懇話会の掲載ページ（町のサイト 0000006543）には、議事録8回分・令和4年度中間報告書・提言（最終報告）の10本がある。議事録は第8回まで（2022年7月12日〜2024年1月12日）。hino-town-docs に取り込んだ（5d0c09a）
- 広報ひのでは、No.780（2025年7月）が再編整備計画の策定、No.792（2026年7月）が再編整備の進め方の記事で、No.792 に「開園時期：令和11年４月（予定）」「施設の確実な整備と安全性・品質確保を優先する観点から、開園時期（当初：令和10年４月）を見直しました。」とある。2025年6月の会議録では、子ども支援課長が「令和10年度の開園をめどに」と答えている
- 広報ひのの縦書きの本文では、縦中横の数字が文から抜けて別の箇所に出ることがある（hino-town-docs koho-no742-03・koho-no766-02）

これを受けて、DESIGN.md に ADR-19 を書き、ADR-14 に広報ひのの数字の扱いを足した。資料の周りの情報と網羅のしかたは判断事項18 とした。広報ひのの取り込む範囲は、hino-town-docs で記事の構造を調べてから決める。
