# 日野町 論点ノート 設計案

Oct 9, 2026 · @ひがし

## 概要

計画・予算・決算・議会の公開資料を、事業や地域課題ごとに整理し、出典とあわせて示す仕組みを作る。仮称は hino-ronten（論点ノート）。

使うデータは次の3系統。

- 計画（shiga-hino-plans）：町が計画で定めた目標・指標・事業。出典は honpen p.N
- 議会だより（council-dashboard）：一般質問の質問と答弁の要約（編集版）。テーマ分類あり
- 会議録（hino-council-search）：発言単位の全文。原本PDFへのリンクあり

評価や結論は記載しない。資料を比較して確認すべき点を示すところまでとし、判断は利用者が行う（council-dashboard の EDITORIAL\_POLICY と同じ方針）。

## 機能の構成

4つの機能に分ける。資料の整理（資料編）と論点の整理（論点編）を別の機能とし、職員向けに2つの機能を加える。画面はメニューで切り替える別画面とし、資料・プロンプト台帳・AIの呼び出し口は共通とする。画面イメージは[論点ノート 画面イメージ](https://claude.ai/artifact/GkbLo9kdHwkWeB7deqszva)。

| 機能 | 内容 | 利用者 | AIの役割 | データ区分 |
| --- | --- | --- | --- | --- |
| 資料編 | 事業ごとに目的・予算・実績・成果指標を一覧にし、出典を示す | 職員・議員（最終的に一般公開） | 抽出・照合の候補作成のみ。職員が確認（ADR-7 と同じ） | 公開 |
| 論点編 | 資料編の内容を比較し、論点を示す | 職員・議員（最終的に一般公開） | 出典つきの案を作成。職員が確認 | 公開 |
| プロジェクトマネジメント編 | 担当事業のロジックモデルを作成し、予算要求・決算説明の文案を作る | 職員 | 記載漏れ・不整合の確認、文案作成 | 庁内 |
| ロールプレイ研修 | 議会答弁・住民説明・予算査定の練習 | 職員 | 架空の質問者役、回答内容の確認 | 公開の題材＋職員の入力 |

機能間の関係は次のとおり。

- 資料編は資料に書かれている内容だけを持ち、解釈を加えない
- 論点編は資料編にない事実を使わない
- PM編・ロールプレイ研修は資料編を参照するだけで、変更しない

### 共通部分

- 資料：一次資料の台帳、事業・計画・指標・質問・発言、リンク台帳
- プロンプト台帳：git の prompts/ に、全機能共通のルール（出典必須・推測禁止・順位付け禁止・実在の人物を模さない）と機能別の指示を版ごとに置く。各プロンプトにモデル区分・出力形式（出典つきか JSON か）・データ区分・評価セットを記載する
- AIの呼び出し口：1か所にまとめ、プロンプトのデータ区分で処理先を決める。庁内区分のプロンプトは国内リージョンの処理先にしか送らない
- 記録：回答ごとにプロンプトのIDと版、モデル名、トークン数を記録する
- 認証：利用者の区分（職員・議員・公開）でメニューを切り替える

## 資料編の材料と不足

議員からの要望（事業の目的・実績・成果を一覧にし、総合計画と予算の関係を示す）に必要な材料は、公開資料でおおむね揃う。不足は、事業と成果指標の対応表と、決算の成果資料の2点。

| 資料 | 単位 | 記載項目 | 不足する項目 |
| --- | --- | --- | --- |
| 第6次総合計画 | 政策の柱5・政策10・分野34（めざす姿） | 体系と将来像 | — |
| 実施計画（R8〜R10、毎年度見直し） | 分野ごとの主要事業 | 事業名・概要・実施年度・3年分の概算事業費 | 担当課・財源・指標 |
| 当初予算の附表「主な事業」 | 政策の柱5つで分類 | 款・事業名・概要・予算額・担当課・新規/拡充 | 分野・施策との対応 |
| 決算 | — | — | 成果を説明する書類は町のサイトで確認できず（今回の検索範囲）。入手先を確認する |
| 個別計画（43本） | 施策 | 目標値・現状値（honpen p.N） | 事業との対応 |
| 議会だより・会議録 | 質問・発言 | 質問と答弁 | — |

当初予算の附表の5分類は、実施計画の政策の柱と同じ名称のため、柱の単位では対応が取れる。分野より下は事業名による照合が必要で、資料編の主な作業となる。成果指標は個別計画にしか記載がないため、事業と指標の対応表を作れるかどうかで、要望に応えられる範囲が決まる。

出典：[実施計画](https://www.town.shiga-hino.lg.jp/0000005740.html)・[令和7年度予算](https://www.town.shiga-hino.lg.jp/0000008184.html)（附表「令和7年度に取り組む主な事業」を含む）

### 公開されていない資料

- 予算書・予算説明書、決算書、主要な施策の成果を説明する書類：議会には提出されるが、町のサイトにない。事業単位の決算額と成果は、現状では取れない
- 総合計画の評価資料と成果指標の実績：総合計画懇話会は中間見直しの会議を2026年7月・9月に開いたが、会議録・資料は掲載されていない
- 事務事業評価、委員会の会議録、施設カルテ、補助金の交付実績：見当たらない

これらは町にサイトでの公開を依頼するか、公開済みの資料の範囲で作る。資料編の「実績」と「成果」の列は、当面は総合戦略の検証報告書と交付金の効果検証で埋められる範囲に限られる。

### 取り込みの注意

- 住民基本台帳の人口PDFは直近12か月分しか掲載されないため、毎月保存する仕組みを先に作る（町のサイトに接続できるPCで定期実行）
- 機械で読める形式は、財政状況資料集・固定資産台帳・県の推計人口・BODIK のデータだけ。ほかはPDFで、計画と同じ前処理（テキスト化・表の抽出・職員の確認）が要る
- 議員別の賛否（議会だよりのPDFに掲載）と選挙結果は、EDITORIAL\_POLICY に沿って順位付けに使わない
- 他団体との比較データは取り込まず、国のツールへのリンクで示す（国のダッシュボードと重複させない方針）
- 年度の欠け（決算の概要のH29〜R1、財政事情の公表のH30〜R2 など）は欠けのまま表示し、推計で埋めない

## 計画名による照合の試算

議会だよりの一般質問326問のうち、計画名を含むものは59問（約18%）。名称の一致だけでは8割が対応しないため、事業名による照合と、分類間の対応表が必要。

| 計画 | 照合した語 | 議会だより（問） | 会議録（出現回数） | 注記 |
| --- | --- | --- | --- | --- |
| sogo6 | 総合計画 | 20 | 968 | 第5次と第6次を区別できない |
| chiiki-nogyo | 地域計画 | 13 | 274 | 文化財保存活用地域計画・国土強靭化地域計画も含む（過大） |
| bunkazai | 文化財保存活用地域計画 | 7 | 107 |  |
| youho | 幼児教育保育施設再編整備計画 | 6 | 51 |  |
| bosai | 地域防災計画 | 5 | 71 |  |
| kodomo | 子ども・子育て支援事業計画 | 5 | 28 | 第2期と第3期を区別できない |
| kyoiku3 / kyoiku4 | 教育振興基本計画 | 4 | 48 | 第3期と第4期を区別できない |
| kankyo | 環境基本計画 | 3 | 85 |  |
| toshimaster | 都市計画マスタープラン | 0 | 44 | 議会だよりの要約には出てこない |
| suido2 | 水道ビジョン | 0 | 25 | 議会だよりの要約には出てこない |

照合方法：正式名から「第N期」「日野町」括弧書きを除いた語を NFKC 正規化し、部分一致で数えた。会議録は議長発言を除外。概算であり確定値ではない。下の2行は会議録では言及があるが議会だよりでは0件で、要約版だけでは計画との対応が取れない例。

試算で判明した課題は次の6点。

1. 名称の重複：「地域計画」は他の計画名の一部でもある。最長一致と除外語の辞書が必要
2. 期の判別：「総合計画」「教育振興基本計画」は名称だけでは何期か判別できない。発言日と計画期間で判別する系譜表が必要
3. 位置に依存するキー：会議録の sid は末尾が連番（\_0003）で、抽出をやり直すと変わる可能性がある。ADR-7 で block\_no をキーから外したのと同じ問題のため、sid と本文ハッシュで照合し、不一致ならビルドを停止する
4. 期間の差：テーマ分類があるのは議会だより第24号（R5年6月）以降のみ。2017〜2023年の一般質問は gian.json に議員名はあるがテーマは空
5. AIが作成したデータ：highlights.json は source が curated(claude-analysis)。論点の根拠には使わず、候補作成の参考に限る
6. 公開版との差：DESIGN.md の ADR-7 が定める data/audit\_log/ と tools/audit\_worksheet.py が、shiga-hino-plans の公開版にない。未pushのコミットがあれば、接続作業の前に push する（新リポジトリは公開版を参照するため）

## 設計の要点

横断のリンクと論点は新しいリポジトリで管理する。機械による処理は候補の作成までとし、確定は職員が行う。

&#91;embedded content: データの流れ · 入力3つ、参照表3つ、人の確定1段\]

3リポジトリの公開データを、版を固定して読み込み、参照表を使って候補を作る。職員が確定したリンクだけを論点カードと出力に使う。

### 1. 新しいリポジトリを設ける

リンクと論点は3リポジトリすべてのデータを使うため、いずれか1つに置くと依存関係が逆になる。3リポジトリは一次データの整形に限定し、横断部分は hino-ronten（仮）に置く。ADR-1（単一正典）と同じ考え方。

- inputs.lock.json に3リポジトリのコミットSHAを記録し、ビルドはそのSHAの公開データを読む（再現性の確保）
- 全文コーパス（index.json 約45MB）は取り込まない。カードには抜粋・sid・原本PDFのURLのみを持たせ、オフライン用HTMLも作れるようにする
- 既存の統合MCPを拡張し、計画とリンクのデータも参照できるようにする

### 2. 共通の分類軸は第6次総合計画の施策体系とする

- 町が定めた体系のため、軸そのものに出典（honpen p.N）があり、分類の妥当性を説明しやすい
- 個別計画は総合計画を上位計画としている（parent\_plan）ため、計画側の対応は文書で確認できる
- 既存の3分類（11テーマ・15トピック・9cat）は残し、軸との対応表で関係づける。対応表は人が作成し、1行ごとに根拠を記載する
- 前提として sogo6 の構造化が必要（data/plans/sogo6.json は未作成）

### 3. リンクは台帳で管理する

ADR-7 の検収台帳と同じ方式で、links/\*.tsv を正本とする。

| 列 | 内容 | 例 |
| --- | --- | --- |
| from | 議会側のキー | bq:36/谷口智哉/1、sp:sid#本文ハッシュ8桁 |
| to | 計画側のキー | plan:sogo6、node:kodomo/第1節/(1)/① |
| method | 照合方法 | mention・program・crosswalk・semantic |
| evidence | 一致した語と位置 | 「第6次日野町総合計画」q 第1段落 |
| status | 状態 | candidate・confirmed・rejected |
| reviewer / date | 確定した人と日付 | ひがし 2026-10-xx |

照合方法は信頼度の高い順に次の4つ。

1. mention：計画名の明示的な言及。系譜表で期を判別する
2. program：事業名・固有名詞の一致（kodomo の100事業など）
3. crosswalk：テーマ対応表を経由する。精度が低いため閲覧の入口に使い、論点の根拠にはしない
4. semantic：既存の埋め込み（transformers.js）による類似度。候補作成のみで、自動では確定しない

論点カードには confirmed のリンクだけを使う。rejected も削除せずに残し、再生成で同じ候補が再び出ないようにする。

### 4. 論点カードの構成

1枚につき1つの地域課題を扱い、次の3項目で構成する。

- 計画の記載：目標・指標・事業（honpen p.N）
- 議会での質問と答弁：議会だより（要約）と会議録（全文）を時系列で示す
- 比較して分かること：機械的に示せる事実の比較のみ。計画の目標値と答弁で示された数値・時期、計画に事業があるが議会で取り上げられていないもの、議会で繰り返し取り上げられているが計画に位置づけがないもの

最後の項目のうち、計画と議会の一方にしか出てこない事項の一覧は、議論の材料として特に有用。文章は論点の形で示し、結論は記載しない。AIが案を作る場合も、confirmed のリンク先の原文だけを材料とし、1文ごとに出典を付け、議員の順位付けはしない。

### 5. 出力

- 静的サイト（GitHub Pages・vanilla）：論点一覧、計画と議会の対応状況の一覧、論点カード
- MCP：論点カードの取得、計画・質問・発言のいずれからも引けるリンク検索、施策ごとの計画記載と議会言及の件数

## 運用の前提

職員による実証から始め、必要に応じて一部の議員、最終的に職員・議員・一部の住民へ利用を広げる。当面は自費で運用し、広報費・研修費等での予算化は実証の結果を見て検討する。

- 応答速度は優先しないが、精度は下げない。待ち時間は精度を上げる処理に充てる
- 利用者の入力・ログ・AIの推論処理は国内リージョンで行う
- 利用者が増えても作り直しにならないよう、特定の基盤に依存しない構成にする

国内リージョンの対象範囲は「利用者の入力・ログ・AI推論の処理」と解釈している。公開情報のみを扱う静的配信とビルド処理を含めるかは、判断事項とした。

## AIモデル

国内で処理できる Claude は、Amazon Bedrock の日本プロファイル（東京・大阪間で処理）経由の Claude Haiku 5.5 と Claude Sonnet 4.6。Sonnet 5.5 は国内で完結する経路がない。回答には Haiku 5.5 を使い、評価の結果が不十分な場合は Sonnet 4.6 に切り替える。

| 経路とモデル | 国内で処理 | 単価（入力／出力） | 機能 |
| --- | --- | --- | --- |
| Bedrock 日本プロファイル・Haiku 5.5（jp.anthropic.claude-haiku-5-5） | する | 0.10／0.50 の1割増し（見込み） | Citations ○、構造化出力 ×、バッチ × |
| Bedrock 日本プロファイル・Sonnet 4.6（jp.anthropic.claude-sonnet-4-6） | する | 3／15 の1割増し（見込み） | Citations ○、構造化出力 ○、バッチ 記載なし |
| Bedrock グローバル・Sonnet 5.5 | しない | 2／10 | Citations ○、構造化出力 ×、バッチ × |
| Anthropic API・Haiku 5.5／Sonnet 5.5 | しない（米国かグローバルのみ） | 0.10／0.50、2／10 | Citations ○、構造化出力 ○、バッチ半額 |

単価は100万トークンあたりの米ドル。Anthropic はリージョン指定のエンドポイントをグローバルより1割高いとしているが、AWS の料金ページに5.5系の東京価格の記載がなく、見込み値とした。Citations の Bedrock 対応は統合単位の記載で、東京の扱いについて Anthropic と AWS の資料に相違がある。日本プロファイルで動作するかは実機で確認する（進め方に記載）。

応答時間の余裕は、次の方法で精度を上げるために使う。

1. 推論の深さ（effort）を上げる。Haiku 5.5 の既定は medium のため high にする
2. 回答の作成後、引用ごとに原文と照合する検証処理を追加で実行する
3. Citations で引用元のない文を表示しない
4. 検索で渡す資料は多めにするが、Haiku 5.5 は1回10万トークンを超えると単価が5倍になるため、その範囲に収める

ビルド処理（候補判定・カード案）は公開情報のみを扱う。これも国内に限る場合は Sonnet 4.6（国内）、限らない場合は Anthropic API の Sonnet 5.5 とバッチ処理（半額）を使う。モデル名は設定値とし、台帳に使用したモデルとプロンプトの版を記録する。

## 段階0（試作）の構成

試作は Cloudflare Workers 上に Hono で構築し、AI は Anthropic API を直接呼び出す。扱うのは公開情報のみとし、庁内情報を扱うPM編は段階1（AWS 東京）から提供する。

- 構成：画面とAPIは Workers、データは D1（SQLite と同じSQL）、AI は Anthropic API
- 提供範囲：資料編・論点編・ロールプレイ研修（練習用アカウント）。PM編は見本画面のみ
- モデル：Sonnet 5.5 と Haiku 5.5 が使え、Citations・構造化出力・バッチ処理も利用できる。モデルの選択肢は段階0の方が多い
- ログイン：Cloudflare Access の無料プラン（50人未満向け）で、招待した職員・議員に限定する
- 注意：段階0では質問文が国外で処理される。利用者に説明し、個人情報・庁内情報は入力しない運用とする

段階1への移行時に変わるのは、実行環境・データ・AIの3点。それ以外のコードはそのまま使う。

| 部分 | 段階0（試作） | 段階1（実証） |
| --- | --- | --- |
| 実行環境 | Cloudflare Workers | AWS Lambda（東京） |
| アプリ | Hono | 同じコード（Hono は Workers と Lambda の両方で動作） |
| データ | D1 | コンテナ内の SQLite（同じSQL） |

モデルが Sonnet 5.5 から日本プロファイル（Haiku 5.5・Sonnet 4.6）に変わるため、切り替え前に評価セットで精度の差を測定する。D1 の全文検索は日本語の分かち書きをしないため、事前の分かち書きが必要。

## 段階1以降の基盤

実証は AWS 東京に集約する。国内で Claude を使える経路が Bedrock のみのため、対話サーバーも同じアカウントの東京リージョンに置く。

| 層 | 利用者 | 配置先 | 国内リージョン |
| --- | --- | --- | --- |
| 公開ページ（論点一覧・対応状況・カード） | 誰でも | GitHub Pages | 判断事項。公開情報のみで入力なし。必要な場合は同じファイルを東京に配置 |
| 対話（質問に出典つきで回答） | 職員→議員→一部住民 | AWS 東京：コンテナ1つ＋Bedrock 日本プロファイル | 対象 |
| ビルド（候補判定・カード案） | ひがし | Claude Code、定期実行にする場合は GitHub Actions | 判断事項 |
| MCP | 将来の外部AIクライアント | 対話と同じコンテナ | サーバーは対象。クライアント側のAI処理は国外になる場合がある |

MCP について：職員が Claude Desktop などから MCP 経由で利用すると、質問文はそのクライアントのAIで処理され、国外に送られる。実証での対話は、独自の画面と Bedrock で国内に限定する。

### 移行しやすい構成

- 1つのコンテナに、SQLite の全文検索（FTS5、日本語は trigram）と日本語の埋め込みモデルを含める。外部のデータベースは使わない
- 埋め込みは ruri-v3（Apache 2.0、CPUで動作）に変更する。モデルカード記載の JMTEB 平均は 130m が76.55、310m が77.24
- Claude の呼び出し処理は1か所にまとめる。Anthropic の SDK に Bedrock 用のクライアントがあり、Anthropic API との切り替えはエンドポイントとモデルIDの設定で行える
- 同じコンテナイメージを Lambda、ECS、Cloud Run、さくらの AppRun で動かせる
- 正本は git の JSON。データベースと埋め込みはビルド時に作る派生物（ADR-1）

### 実証期と拡大期

実証期は Lambda のコンテナ（最大10GB）を Function URL で公開し、応答はストリーミングで返す（2026年4月から全商用リージョンで利用可）。1回の実行上限は15分、無料枠は月100万リクエスト・40万GB秒。Python の場合は Lambda Web Adapter を使えば通常のWebサーバーとして動く。初回起動時はモデルの読み込みに数秒以上かかる場合があるが、実証では許容する。ログインは招待制とする。

拡大期は、同じイメージを常時起動の ECS に移すか、町がガバメントクラウドで契約する基盤に載せる。令和8年度のガバメントクラウドは AWS・Google Cloud・Azure・OCI・さくらのクラウドで、さくらは2026年3月27日に全要件への適合が確認された。Cloud Run（東京）も無料枠と MCP の公式ガイドがあり候補になるが、Claude は Bedrock を使うため、クラウドが2つに分かれる。

## 進め方

子育て分野で先に一通り作り、その後、総合計画の施策体系を軸に他分野へ広げる。kodomo は分類軸がなくても直接対応づけられるため、sogo6 の構造化を待たずに着手できる。各工程は Claude Code への「ここから／ここまで」形式の指示で1つずつ進める。

1. 確認：shiga-hino-plans の未push分の有無と、下の「判断事項」
